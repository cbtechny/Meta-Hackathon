# Part cards in the chat

Implemented November 3, 2026. Retrieved part cards now appear directly beneath their assistant reply. The separate results panel under the lookup sidebar and the extra reveal/acknowledgment button are removed from chat. The original non-chat lookup page retains its existing configuration acknowledgment.

## Visible result

Each card immediately shows the retrieved part name, number as text, brand, and either **Demo part — simulated fitment** or **Verified source record**. The associated catalog configuration is shown without copying unknown equipment into customer details. Verified records show their verification date. Source statements and restrictions are available through a keyboard-accessible disclosure.

The newest card is scrolled into view without skipping its part number. The lookup sidebar remains available for editing details. An incompatible correction leaves no active matching card; older cards stay attached to their original replies and are labeled **Previous result**, with old follow-up buttons disabled.

## Confirmed-details count

The backend returns `lookup.detail_progress` with `confirmed`, `total`, `confirmed_fields`, `unconfirmed_fields` and an explanation. The fixed six fields are **year, make, model, engine, trim and drivetrain**, equally weighted. The UI displays **Vehicle details confirmed: X of 6** with a detail-completeness bar. It is not a fitment probability, confidence percentage, compatibility guarantee or availability claim; even 6 of 6 establishes none of those things.

Only customer-provided/overridden facts and explicitly accepted VIN facts count. Catalog defaults, demo-profile selections, unaccepted VIN values, unknowns and inferred equipment do not count. Repeating a demo value explicitly, such as `2.5L`, can confirm that fact without changing its value. Trim/drivetrain values inferred from catalog context are excluded from customer facts. Progress comes from the existing server conversation state and is never generated by Meta or calculated from browser input.

## Follow-up behavior

Required questions that distinguish actual loaded applications still come first. A preview stays visible while the backend asks one optional remaining detail, in engine/trim/drivetrain order, provided that detail exists in the relevant loaded profiles. **I don't know / skip** leaves the unknown unresolved and moves on. Skipped optional fields remain skipped through subsequent answers and part changes; changing the vehicle or starting over resets that choice. Supplying a skipped value explicitly makes it confirmed and eligible for normal matching again.

Existing VIN conflict/acceptance, correction rules, sessions, revisions and request deduplication remain authoritative. A newly decoded VIN requires acceptance before its decoded facts increase the count. Failures preserve confirmed facts and pending user text; retries do not duplicate messages or inflate the count.

## History, migration and privacy

Card snapshots are saved separately from plain `{role, content}` conversation messages in the existing tab-scoped `sessionStorage`, within the retained 60-message history. Snapshots preserve the original card, count and question after reload. They are not sent to Meta as history, and no new conversation database or matching engine is introduced. New conversation clears the text and snapshots and ignores any late in-flight reply.

Older saved conversations without snapshots can restore their latest retrieved result inline. If that response predates progress metadata, the page says the count will update with the next lookup rather than inventing a number. Existing server session expiry/restart behavior remains: cached cards can be viewed, but an expired server session requires New conversation to continue.

All rendering uses DOM text operations. API credentials remain backend-only; no new credential access, external browser assets or model calls are introduced by the card UI. Rendering/expanding a card makes no API call. Answering an ordinary chat question uses the existing Meta path; panel edits use the existing deterministic correction path.
